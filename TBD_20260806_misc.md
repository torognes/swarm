## T1 — a strongly typed `threads` option

**Not done. The premise has shifted: the checks are already centralised;
only the type is still bare.**

Where things stand:

- `Parameters::opt_threads` is a plain `std::uint32_t`, `src/swarm.hpp:52`
- the constraints live in `validate_threading(int64_t) -> std::uint32_t`,
  `src/cli.cpp:393-400`: range 1 to 512, `fatal()` otherwise, called once
  at parse time from `src/cli.cpp:563`. The comment block above the
  per-option validators already spells out the "range-check the signed
  value, then narrow" contract this item was asking for
- `man/swarm.1:175-178` agrees on 1 to 512. No manual/behaviour discrepancy
- nine sites touch the value: six hand it straight to a `std::size_t`
  (the `ThreadRunner` constructor, `std::vector` sizes), one to
  `Scanner::n_threads_` which is `uint64_t` (`utils/scanner.hpp:117`),
  one logs it, one assigns it

So what is missing is not validation but a *type that carries the
invariant*. `fatal()` is `[[noreturn]]` (`utils/fatal.hpp:34`), so a
validating constructor is well-formed even under `-fno-exceptions`.

**Feasibility: easy.** Roughly a 60-line `utils/thread_count.hpp` plus the
nine call sites.

**Blocked on three decisions:**

1. **"Direct export to `uint64_t`."** An *implicit* `operator uint64_t`
   would let `opt_threads * 2` compile silently, giving back most of what
   the strong type was meant to prevent. Six of the eight consumers want
   `std::size_t`, not `uint64_t`; only `Scanner` wants the latter. A named
   accessor returning `std::size_t`, plus an `explicit operator
   std::uint64_t`, fits the call sites better and stays inside the
   "avoid implicit conversions" grain of `CLAUDE.md`. The implicit
   conversion is what the note asks for, though, so this needs a ruling.
2. **Who calls `fatal()`.** Calling it from the constructor couples a
   domain type to the CLI error path. Alternative: keep
   `validate_threading` in `cli.cpp` as the factory, and let the class
   only `assert()` its invariant.
3. **`adjust_thread_number`** (`utils/scanner.cpp:82-95`) *shrinks* the
   count and returns `uint64_t`. A strong type needs a sanctioned way to
   build a smaller count without re-running CLI validation — a
   `capped_at()` member, say. Otherwise that function keeps trafficking
   in bare integers and the type stops at the constructor.


## T2 — `-Wcast-align=strict`

**Not done. Plain `-Wcast-align` has been on since the DEBUG warning set
was assembled (`src/Makefile:34`); `=strict` is the increment.**

Two of the eight sites in the January note are genuinely gone:

- `variants.cc:42` `nt_set` now round-trips the 64-bit word through
  `std::memcpy`, `utils/variants.cpp:52-56` — that fixed the strict
  aliasing violation and the alignment cast together
- `scan.cc:120` no longer casts; the cast moved into `search16.cpp:487`
  when the scanner was split up

Current inventory: 11 warnings on x86-64, 7 on aarch64, 7 on ppc, 0 on the
portable fallback. Three distinct root causes.

### Group A — `hearray_v` is a `std::vector<BYTE>`

`search16.cpp:487`, `search16.cpp:525`, `search8.cpp:780`. All three
arches, one cause: `Search_data::hearray_v` at `utils/search_data.hpp:43`.

**This one deserves fixing whether or not the flag ever goes on.** The
kernels dereference `__m128i*` / `uint8x16_t*` / `vector unsigned char*`
directly — that is an *aligned* load on each ISA — and it works today only
because `operator new` happens to return `alignof(std::max_align_t)`
storage, which is 16 on these three targets. Nothing in the code says so.
On x86-64 the requirement sits exactly at the guarantee, with no margin.

Fix: give `hearray_v` an over-aligned element type, mirroring the
`Qgram_vector` pattern already used for the qgram store
(`utils/qgram_array.hpp:38-44`, whose comment explains the same reasoning).
Costs a ceil-divide where `utils/scanner.cpp:74` resizes in bytes
(`ceil_divide.hpp` already exists) and rounds the budget line at
`utils/scanner.cpp:63` up by under 16 bytes.

### Group B — the qgram compare signature erases an alignment that exists

Two warnings in each of `arch/x86_64/qgram_compare.cpp`,
`arch/aarch64/qgram_compare.cpp`, `arch/ppc/qgram_compare.cpp`, plus two
in `arch/x86_64/popcnt.cpp:50-51`. `arch/portable/qgram_compare.cpp` is
clean because it uses `std::memcpy`.

`Qgram_vector` is already `alignas(16)` (`utils/qgram_array.hpp:44`). The
alignment is then thrown away by the kernel signature,
`compareqgramvectors(unsigned char const *, unsigned char const *,
Cpu_features const &)` (`utils/qgram_compare.hpp:40`). The contract
survives only as an assert and a comment at
`arch/x86_64/qgram_compare.cpp:109`: *"input MUST be 16-byte aligned"*.

Fix: take `Qgram_vector const &`. The cast then starts from an
over-aligned type and the diagnostic goes quiet for the right reason —
the contract becomes a type-level fact instead of a comment.

**Blocked on a decision:** this is a signature change rippling to
`utils/qgram_compare.hpp`, four `arch/*/qgram_compare.cpp`,
`arch/x86_64/popcnt.{cpp,hpp}`, and the single caller `utils/qgram.cpp:95`.

### Group C — the intrinsics wrappers *are* the cast

Four warnings in `arch/x86_64/intrinsics_to_functions.cpp` (lines 37, 41,
45, 49 — `cast_vector16` and `cast_vector8`, const and non-const), two in
`arch/aarch64/intrinsics_to_functions.cpp:82,86`, two in
`arch/ppc/intrinsics_to_functions.cpp:84,93`.

**Not fixable in C++11, only suppressible.** There is no standard way to
say "this `uint8_t*` is 16-byte aligned": `std::assume_aligned` is C++20,
and `__builtin_assume_aligned` is a GNU extension returning `void*`.
Concentrating the cast in these wrappers is the design — on aarch64
`cast_vector8` is very nearly a no-op, as its own comment at
`search8.cpp:779` notes.

Two options:

- a scoped `#pragma GCC diagnostic push` / `ignored("-Wcast-align")`
  around the wrappers, with a comment naming the caller's obligation.
  About four lines in each of three arch files
- hop through `static_cast<void const *>` first. Verified to silence GCC,
  and needs no pragma — but it launders exactly the information the
  warning carries, so it reads as a fix while being a suppression

The pragma is the honest one.

### The mechanism that makes A and B real fixes

GCC stops warning when the *source* pointer type is itself over-aligned.
Confirmed directly:

```cpp
struct alignas(16) Block : std::array<unsigned char, 16> {};
reinterpret_cast<__m128i *>(uchar_ptr);   // warns
reinterpret_cast<__m128i *>(block_ptr);   // silent
reinterpret_cast<__m128i *>(blk.data());  // warns — data() hands back unsigned char*
```

The third line is why group B has to move the alignment into the
*signature* rather than casting from `.data()` inside the kernel.

### Packaging

`-Wcast-align=strict` belongs in `DEBUG_WARNINGS_GCC`, not
`DEBUG_WARNINGS_COMMON`: clang does not accept the `=strict` spelling, and
its plain `-Wcast-align` is already machine-independent. **Unverified** —
no clang on this machine.

### Suggested order

A first, as standalone hardening. Then B, if the signature change is
approved. Then C's pragmas. Only then flip the flag. If the pragmas are
unwelcome, keep plain `-Wcast-align` and still take A and B — both stand
on their own.


## T3 — `std::size_t` for loop counters

**Not done, and mostly moot as written. Four real sites inside it.**

Exactly one counted loop in the tree uses `size_t`; 23 use `0U`, about ten
use `0ULL` or `0UL`.

But the tree has since settled on `unsigned int` as *the* amplicon-index
type. `Data::sequence_count()` returns `unsigned int` (`db.hpp:72`), and
`no_swarm` is `std::numeric_limits<unsigned int>::max()` used as a sentinel
(`utils/algod1_internal.hpp:51`), so amplicon counts are deliberately
capped below `UINT_MAX`. Loops bounded by that count — `algod1.cpp:301`,
`utils/algod1_network.cpp:177`, `utils/qgram.cpp:80`,
`utils/algod1_fastidious.cpp:152` — have counters that match their bound
*exactly*. Retyping them to `std::size_t` would introduce a widening
comparison and buy nothing. The same goes for the fifteen or so loops
bounded by a small `constexpr unsigned int` (`channels`, `cdepth`,
`nt_per_byte`, `pattern_k`, `byte_range`). The `0ULL` loops are already
64-bit, which is `std::size_t`'s width on every target swarm builds for.

The genuine mismatches are the four loops whose bound is a container's
`.size()`:

| site | loop |
|---|---|
| `dereplicate.cpp:311` | `for (auto seqno = 0U; seqno < nextseqtab.size(); ++seqno)` |
| `utils/algod1_output.cpp:82` | `for (auto i = 0U; i < swarminfo_v.size(); ++i)` |
| `utils/algod1_output.cpp:115` | `for (auto i = 0U; i < swarminfo_v.size(); ++i)` |
| `utils/algod1_output.cpp:287` | `for (auto swarmid = 0U; swarmid < swarminfo_v.size(); ++swarmid)` |

A 32-bit counter against a 64-bit bound. The comparison itself is safe —
the counter widens — but past `UINT_MAX` elements the loop would never
terminate. In practice the same amplicon cap keeps it out of reach, so
this is a wrong type rather than a live bug.

**`std::size_t` is the wrong direction for all four.** Two readings that
looked right from the loop headers alone did not survive contact with the
bodies:

- *"the counters only index, so make them range-for."* No: each of the
  three feeds `progress.update(i + 1)`, and because the loops `continue`
  past attached clusters, that absolute index is what keeps the progress
  bar accounting for skipped entries. `progress.increment()` would count
  only processed ones and finish short of 100 %
- *"`seqno` should be `std::size_t`."* No: `seqno` is stored back into
  `nextseqtab[…]` (`std::vector<unsigned int>`) and into
  `bucket::seqno_first` and `seqno_last`, both `unsigned int`
  (`dereplicate.cpp:350,357,363`). Widening the counter moves the problem
  to the stores, which would then narrow — and `-Wconversion` is on in
  DEBUG

Both counters are *ids*, and this tree addresses amplicons and clusters
with `unsigned int` throughout: `ampinfo_s::swarmid`, `bucket::seqno_*`,
`nextseqtab`'s element type, `cluster_members(…, unsigned int const seed)`,
with `no_swarm` reserving `UINT_MAX`. A loop counter's type is fixed by
where its value is *stored*, not by the `size_type` of whatever container
supplies the bound. So the fix is to bring the bound down to the id type,
not the counter up to `size_type`.

Implemented in `f7c8b28`:

- `cluster_count()` in `utils/algod1_output.cpp` states once what the three
  writers each relied on silently — a cluster count fits in an
  `unsigned int` because a `swarmid` does — and the three loops take their
  bound (and their `Progress` size) from it
- `dereplicating()` asserts `nextseqtab.size() == data.sequence_count()`
  and bounds its loop by that `unsigned int` count, matching the
  `const auto amplicons = data.sequence_count();` idiom already at
  `algo.cpp:298` and `utils/algod1_network.cpp:169`
- the two writers that called their counter `i` now call it `swarmid`, the
  name the third already used and the name of the thing that indexes
  `swarminfo_v` everywhere else. Also clears the sub-three-character
  identifier rule

Verified: DEBUG build warning-free on x86-64; `aarch64`, `ppc64le` and
mingw cross-builds clean; `cppcheck` clean on both files; the test suite
runs to completion, 1066 PASS / 0 FAIL.

**What should be recorded for the rest of the item:** `unsigned int` is the
intended amplicon- and cluster-id type, so the remaining twenty-odd `0U`
loops are correct as they stand and should not be swept to `std::size_t`.
`std::size_t` belongs where a value really is a size or an offset into a
container — which is where the tree already uses it (`Span`, `View`,
`line_buffer`, `algo_internal.hpp:119`) — and not where the value is an
amplicon id that happens to be used as a subscript.
