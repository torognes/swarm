## T1 — a strongly typed `threads` option

**Done, `364b960` and `232dd61`.** `utils/thread_count.hpp` is about 60
lines; the nine call sites each took one word.

**The premise had shifted since the note was written**, which is worth
recording because it changed what was left to do. The *checks* had already
been centralised: `validate_threading` (`cli.cpp`) held the 1-to-512 range,
called once at parse time, and the comment block above the per-option
validators already spelt out the "range-check the signed value, then
narrow" contract the note was asking for. `man/swarm.1:175-178` agrees on
1 to 512 — no manual/behaviour discrepancy. So what was missing was not
validation but a *type that carries the invariant* past the parser.
`fatal()` is `[[noreturn]]` (`utils/fatal.hpp:34`), so a validating
constructor would have been well-formed even under `-fno-exceptions` — it
just turned out not to be the right place for it (decision 2 below).

### The three decisions, as settled

1. **No conversion operator at all.** The note asked for "direct export to
   `uint64_t`", which reads as an implicit `operator uint64_t` — and that
   would let `opt_threads * 2` compile, handing back most of what the type
   was for. It also turned out to be unnecessary: `std::size_t` is what the
   consumers actually want, in **seven of the nine** reads (five
   `ThreadRunner` constructions, `threads.hpp:80`, plus the per-thread
   vectors in `qgram.hpp:85` and `scanner.hpp:132`). The eighth,
   `Scanner::n_threads_`, took it as a `uint64_t` by widening — and has
   since become a `ThreadCount` itself. The ninth is a template log
   printer. So one `count()` returning `std::size_t` covers everything.
2. **`fatal()` stays in `cli.cpp`.** `validate_threading` remains the
   factory and reports out-of-range input; the constructor only asserts
   what the caller has established. The type does not know about the CLI.
3. **`adjust_thread_number` moved into the type** as `capped_at()`. This
   was the one place a validated count left its type to be manipulated —
   `n_threads_` was a bare `uint64_t` and the reduction decremented a copy
   of it in a loop.

### `capped_at()` and the shape of the reduction

The loop turned out to be a min of a ceiling division:

```
while (remaining <= (n - 1) * channels) { --n; }
  is  min(n, ceil(remaining / channels))
```

Brute-forced over every `(channels, remaining, threads)` triple for
channels in {8, 16}, remaining in 1…20000, and threads across the whole
1…512 range the option allows: **20,480,000 triples, all agreeing.** That
covers the thirteen cases the commented-out table documented.

Three things fall out of the new form:

- one parameter instead of three, so no pair of same-typed parameters to
  swap. `Bit_mode` stays in `scanner.cpp` behind `channels_for()`, keeping
  SIMD lane counts out of a type that only holds a number
- the multiplication is gone, so its overflow guard goes too — and with it
  `ullong_max` and its `[[maybe_unused]]` note. `<limits>` stays for the
  four `gapopen`/`gapextend` asserts. `ceil_divide` asserts its own bound,
  and the `remaining != 0` precondition moved to the call site
- the documented table is kept at the new call site, re-expressed against
  the new decomposition with every case and expected value intact

### Performance: bounded by counting, not by timing

The new form does a hardware **divide** where the old did a compare, so it
was worth checking despite being O(1) against a loop. Timings on this box
were not usable — 15-minute load 3.8, past the threshold that has
invalidated runs here before — so the question was settled with two
load-independent measurements instead:

- **`Scanner::run()` is called 17,004 times** over the whole `-d 10`
  workload (instrumented atomic counter, `perf` does not work on this
  kernel). One extra divide at ~40 cycles is ~0.2 ms against 7.9 s of user
  CPU: **0.003 %**. The arithmetic cannot produce a percent-level effect.
- **`sizeof(Scanner)` is 3296 before and after.** `n_threads_` sits
  immediately before a `std::mutex`, which needs 8-byte alignment, so
  shrinking it from 8 bytes to 4 turned the difference into padding and left
  every member from `scan_mutex_` onward at its original offset — including
  `next_`, `remainingchunks_` and the mutex itself, the fields
  `next_window()` touches under the lock. No layout effect either.

A paired run on the contended box read **+3.2 %** (median of 16
order-alternating pairs, 12 of 16 positive). Given the two bounds above
there was no mechanism for it, and re-measuring on an idle box
(`loadavg` 0.06 / 0.02 / 0.00, 2026-08-07) confirmed it was not real.

**The clean run: neutral.** 16 order-alternating pairs, binaries built from
`364b960` and `232dd61` in separate worktrees so the pair differs only in
`scanner.{cpp,hpp}` and `thread_count.hpp`:

| order group | positive | mean delta |
|---|---|---|
| new first, old second | 7 of 8 | **+0.302 s** |
| old first, new second | 2 of 8 | **−0.133 s** |

The two groups **disagree in sign**: whichever binary ran *second* was
faster, in 13 of 16 pairs, regardless of which binary that was. Solving the
group means for the two effects (`NO = code + P`, `ON = code − P`) gives a
**first-position penalty P = +0.218 s (2.7 %)** and a code effect of
**+0.085 s ± 0.056** (t = 1.51, p ≈ 0.15) — not significant. Per the
standing rule for this host, disagreeing order groups mean the effect is
below the noise floor: **report neutral, not the average of the two.**

That also retro-explains the earlier readings. The first paired attempt used
a fixed "new first" order and got 7 of 12 positive — the same 7-of-8 as this
run's NO group. It was measuring position, not code.

Three method notes, all of which cost time here:

- an initial *sequential* run — all old samples, then all new — read as
  −2.4 %, purely because both binaries climbed from 958 s to 1007 s over the
  session. A/B on this host must be interleaved and read as paired
  differences, never as two blocks
- the first paired attempt used a **fixed** within-pair order, so every
  difference carried the same 2.7 % first-position penalty. Alternating the
  order per pair is what exposes it: with a fixed order the penalty is
  indistinguishable from a code effect, and with alternation it shows up as
  two order groups of opposite sign
- `/proc/loadavg` has to be read *before starting*, not after concluding.
  Had it been checked first, none of the contended runs would have been
  worth doing. Note the 1-minute figure can be inflated by one's own build:
  the clean run started at 2.27 / 0.58 / 0.19, where only the 15-minute
  0.19 was meaningful

`channels` is always 8 or 16, both powers of two, so the divide could become
a shift if it ever does show up — `ceil_divide.hpp:48` points at the
`round_up_to_*` helpers for exactly that. Not done: 0.003 % is not worth
the code.

### Group A — `hearray_v` is a `std::vector<BYTE>`

`search16.cpp:487`, `search16.cpp:525`, `search8.cpp:780`. All three
arches, one cause: `Search_data::hearray_v` at `utils/search_data.hpp:43`.

**Done, `80df510`** — and it deserved doing whether or not the flag ever
goes on. The kernels dereference `__m128i*` / `uint8x16_t*` /
`vector unsigned char*` directly, which is an *aligned* load on each ISA,
and that worked only because `operator new` returns
`alignof(std::max_align_t)` storage — exactly 16 on these three targets, so
the requirement was met with **no margin** and nothing in the code said it
existed. On a target whose `max_align_t` were 8 it would have broken
silently.

`He_block` states it, mirroring `Qgram_vector` (`utils/qgram_array.hpp:38-44`)
including the derivation from `std::array` that keeps `data()` and `size()`.

`search16` also carried a two-step cast, `BYTE * → WORD * → VECTORTYPE *`,
whose `WORD *` step nothing else read and which discarded the alignment on
the way through. Both kernels now cast once, from `He_block *`.

Sizing moves from bytes to blocks: `hearray_blocks` is computed once and the
budget line derives its byte figure back from it, so the two cannot drift.
**No rounding happens** — the byte size is a multiple of `nt_per_uint64`,
itself a multiple of 16, and `sizeof(He_block)` is exactly 16 (checked), so
the allocation is byte-for-byte what it was.

**Verification.** Outputs byte-identical over 16 combinations — 4 inputs
(including 380 bp V4 reads, to push `longestdbsequence`) × d = 1, 2, 5, 10 ×
five output files — plus `-f`, `-t 4`, and the two together. With the default
penalties `d ≤ 6` reaches `search8` and `d > 6` reaches `search16`
(`algo.cpp:59-81`), so both kernels are covered. ASan+UBSan clean on six
runs. Cross-builds clean; `cppcheck` reports nothing HEAD did not already
report (verified against a worktree at HEAD — all seven `unusedStructMember`
hits and both `constParameterPointer` hits are pre-existing single-TU false
positives). Suite 1066 PASS / 0 FAIL.

**No benchmark, and one lesson.** Both kernels are instruction-identical to
before — 904 and 632 instructions, unchanged symbol sizes. Getting there
took a second pass: the first version inlined `.data()` at the cast site and
dropped the `hearray` local, which cost **+2 prologue instructions** to
register reallocation and grew `search8` by 16 bytes. The disassembly showed
it (all hunks confined to instructions 14–103 plus two alignment nops),
keeping the local removed it. `.text` still grows 432 bytes in `algo_run`,
where `allocate_per_thread_search_data` inlines — a fresh
`std::vector<He_block>` instantiation plus the `ceil_divide`, run once per
invocation.

Method note for the disassembly diff: objdump prints jump targets **twice**,
as a bare hex address and as `<symbol+0xNNN>`. Both have to be normalised, or
a function that merely *moved* looks like 80 changed instructions. Stripping
only `0x`-prefixed forms left ~75 phantom hunks and briefly suggested the
inner loops had changed.

### Group B — the qgram compare signature erases an alignment that exists

Two warnings in each of `arch/x86_64/qgram_compare.cpp`,
`arch/aarch64/qgram_compare.cpp`, `arch/ppc/qgram_compare.cpp`, plus two
in `arch/x86_64/popcnt.cpp:50-51`. `arch/portable/qgram_compare.cpp` is
clean because it uses `std::memcpy`.

`Qgram_vector` is already `alignas(16)` (`utils/qgram_array.hpp:44`). The
alignment is then thrown away by the kernel signature,
`compareqgramvectors(unsigned char const *, unsigned char const *,
Cpu_features const &)` (`utils/qgram_compare.hpp:40`). The contract
survives only as an assert and a comment at
`arch/x86_64/qgram_compare.cpp:109`: *"input MUST be 16-byte aligned"*.

**Done, `d1ebb61`.** Takes `Qgram_vector const &`, so the cast starts from
the over-aligned type and the diagnostic goes quiet for the right reason:
the contract is now a type-level fact instead of a comment. Eight files —
`utils/qgram_compare.hpp`, four `arch/*/qgram_compare.cpp`,
`arch/x86_64/popcnt.{cpp,hpp}`, and the single caller `utils/qgram.cpp`.

Inventory after: **x86_64 11 → 7, aarch64 7 → 5, ppc 7 → 5**, portable
still 0. What is left is group A and group C.

Two details that are not obvious from the diff:

- the kernels cast from **`&lhs`, not `lhs.data()`**. `data()` returns
  `unsigned char const *` and would drop the alignment straight back
  again — the whole point. Commented at each of the three SIMD kernels,
  because it reads like a pointless difference. The portable path keeps
  `.data()`, since it `memcpy`s the bytes rather than loading them as
  vectors
- the old `assert(qgramvectorbytes % 16 == 0);` became two `static_assert`s
  that each check what they claim (the size divides evenly into 128-bit
  steps; `alignof(Qgram_vector)` covers the load), and they hold at compile
  time rather than in debug builds only. `<cassert>` left the file with the
  runtime assert. **This replaced a comment and needs a human nod** — the
  claim is preserved, the wording is not

**Verification.** Outputs byte-identical over 18 combinations: 3 inputs (up
to 19,611 sequences) × d = 2, 5, 10 × both x86 kernels, comparing clusters,
internal structure, statistics and uclust. `-x` clears `popcnt_present`
(`cpu_features.cpp:123`), which is how `compareqgramvectors_128` is reached,
and the two kernels agree with each other as well as with the old code.
DEBUG builds carry ASan+UBSan, whose alignment check is exactly this failure
mode; all four runs clean. Cross-builds and `cppcheck` clean; suite 1066
PASS / 0 FAIL.

No timing run, because there was nothing to time: `.text` is identical
(111694 bytes both) and `compareqgramvectors_popcnt` (70 instructions) plus
`QgramDiffer::worker` (237, inlining `qgram_diff` and the compare)
disassemble instruction-for-instruction identically. Only the mangled names
differ. This is the cheap version of the lesson learned in T1 — bound the
mechanism first; here the bound was exact, so the benchmark was skipped
entirely.

### Group C — the intrinsics wrappers *are* the cast

Four warnings in `arch/x86_64/intrinsics_to_functions.cpp` (lines 37, 41,
45, 49 — `cast_vector16` and `cast_vector8`, const and non-const), two in
`arch/aarch64/intrinsics_to_functions.cpp:82,86`, two in
`arch/ppc/intrinsics_to_functions.cpp:84,93`.

**Not fixable in C++11, only suppressible.** There is no standard way to
say "this `uint8_t*` is 16-byte aligned": `std::assume_aligned` is C++20,
and `__builtin_assume_aligned` is a GNU extension returning `void*`.
Concentrating the cast in these wrappers is the design — on aarch64
`cast_vector8` is very nearly a no-op, as its own comment at
`search8.cpp:779` notes.

Two options:

- a scoped `#pragma GCC diagnostic push` / `ignored("-Wcast-align")`
  around the wrappers, with a comment naming the caller's obligation.
  About four lines in each of three arch files
- hop through `static_cast<void const *>` first. Verified to silence GCC,
  and needs no pragma — but it launders exactly the information the
  warning carries, so it reads as a fix while being a suppression

The pragma is the honest one.

**Prototyped and measured (not committed).** The pragma version takes all
three architectures to **zero** `-Wcast-align=strict` warnings, and
`-Wcast-align=strict` then goes into `DEBUG_WARNINGS_GCC` — after which a
plain `make DEBUG=1` builds warning-free with the flag on by default. Total
cost: 13 comment-and-pragma lines in each of the three
`arch/*/intrinsics_to_functions.cpp`, plus 3 lines of Makefile. The regions
are:

| file | suppressed span |
|---|---|
| `arch/x86_64/…` | the four `cast_vector16`/`cast_vector8` overloads |
| `arch/aarch64/…` | `cast_vector8_real`, `cast_vector64` |
| `arch/ppc/…` | `cast_vector8_real`, `v_load16`, `v_load_64` |

Two caveats for whoever applies it. The pragma disables plain
`-Wcast-align` inside the region too, not only the strict variant — which is
the intent for functions whose whole job is that cast, but it does mean a
*genuinely* wrong cast added inside the region would go unreported, hence
popping as early as possible. And the ppc span incidentally covers
`v_load16`, which contains no cast at all; tightening that to exclude it
needs a second push/pop pair or a function reorder.

The patch is `group_c_demo.patch` in the session scratch directory, not on
the branch.

### The mechanism that makes A and B real fixes

GCC stops warning when the *source* pointer type is itself over-aligned.
Confirmed directly:

```cpp
struct alignas(16) Block : std::array<unsigned char, 16> {};
reinterpret_cast<__m128i *>(uchar_ptr);   // warns
reinterpret_cast<__m128i *>(block_ptr);   // silent
reinterpret_cast<__m128i *>(blk.data());  // warns — data() hands back unsigned char*
```

The third line is why group B has to move the alignment into the
*signature* rather than casting from `.data()` inside the kernel.

### Packaging

`-Wcast-align=strict` belongs in `DEBUG_WARNINGS_GCC`, not
`DEBUG_WARNINGS_COMMON`: clang does not accept the `=strict` spelling, and
its plain `-Wcast-align` is already machine-independent. **Unverified** —
no clang on this machine.

### Suggested order

A first, as standalone hardening. Then B, if the signature change is
approved. Then C's pragmas. Only then flip the flag. If the pragmas are
unwelcome, keep plain `-Wcast-align` and still take A and B — both stand
on their own.


## T3 — `std::size_t` for loop counters

**Not done, and mostly moot as written. Four real sites inside it.**

Exactly one counted loop in the tree uses `size_t`; 23 use `0U`, about ten
use `0ULL` or `0UL`.

But the tree has since settled on `unsigned int` as *the* amplicon-index
type. `Data::sequence_count()` returns `unsigned int` (`db.hpp:72`), and
`no_swarm` is `std::numeric_limits<unsigned int>::max()` used as a sentinel
(`utils/algod1_internal.hpp:51`), so amplicon counts are deliberately
capped below `UINT_MAX`. Loops bounded by that count — `algod1.cpp:301`,
`utils/algod1_network.cpp:177`, `utils/qgram.cpp:80`,
`utils/algod1_fastidious.cpp:152` — have counters that match their bound
*exactly*. Retyping them to `std::size_t` would introduce a widening
comparison and buy nothing. The same goes for the fifteen or so loops
bounded by a small `constexpr unsigned int` (`channels`, `cdepth`,
`nt_per_byte`, `pattern_k`, `byte_range`). The `0ULL` loops are already
64-bit, which is `std::size_t`'s width on every target swarm builds for.

The genuine mismatches are the four loops whose bound is a container's
`.size()`:

| site | loop |
|---|---|
| `dereplicate.cpp:311` | `for (auto seqno = 0U; seqno < nextseqtab.size(); ++seqno)` |
| `utils/algod1_output.cpp:82` | `for (auto i = 0U; i < swarminfo_v.size(); ++i)` |
| `utils/algod1_output.cpp:115` | `for (auto i = 0U; i < swarminfo_v.size(); ++i)` |
| `utils/algod1_output.cpp:287` | `for (auto swarmid = 0U; swarmid < swarminfo_v.size(); ++swarmid)` |

A 32-bit counter against a 64-bit bound. The comparison itself is safe —
the counter widens — but past `UINT_MAX` elements the loop would never
terminate. In practice the same amplicon cap keeps it out of reach, so
this is a wrong type rather than a live bug.

The four sites split two ways, and neither way is `std::size_t`.

### The three cluster writers: no counter at all (`89edbb4`)

The counters existed only to index `swarminfo_v` and to feed
`progress.update(index + 1)`, so `Progress::increment()` retires them.
The one subtlety, and the reason a first pass wrongly concluded that
range-for was unavailable here: **`increment()` has to be called above the
`attached` guard, not below it.** Above the guard it counts every cluster,
attached or not, which is exactly what the absolute index was doing. Below
it, it would count only the reported clusters and the bar would finish
short.

`utils/algo_output.cpp:52-54` already documents the same conversion, so
this is house idiom rather than a new pattern. Cost is nil:
`Progress::update` early-returns below its next milestone
(`utils/progress.cpp:55`), so calling it once per cluster instead of once
per reported cluster is two compares and no I/O.

One transient-output change, in the right direction. When the tail of
`swarminfo_v` is attached, the old bar stopped at its last reported cluster
and `done()` supplied the only 100 %. Measured on a two-cluster graft
(`big;size=10` plus a size-1 amplicon two differences away, so the graftee
is attached and last):

```
dev:  Writing swarms:    0%  →  50%  →  100%
new:  Writing swarms:    0%  →  50%  →  100%  →  100%
```

The doubled 100 % is how every other bar in swarm already prints
(`Reading sequences: 100%  Reading sequences: 100%` in the same log); the
short-running bar was the anomaly. Cluster and internal-structure output
are byte-identical.

### `dereplicate.cpp`: keep the counter, fix the bound (`f7c8b28`)

That loop cannot be a range-for. `seqno` is a genuine amplicon id — passed
to `data.sequence_view(seqno)` and `data.abundance(seqno)`, and stored into
`nextseqtab[…]` (`std::vector<unsigned int>`) and into
`bucket::seqno_first` and `seqno_last`, both `unsigned int`
(`dereplicate.cpp:350,357,363`) — and `nextseqtab` is written at arbitrary
positions rather than swept in order.

`std::size_t` would be wrong for it too: widening the counter only moves
the problem to those three stores, which would then narrow, and
`-Wconversion` is on in DEBUG. The counter's type is fixed by where its
value is *stored*, not by the `size_type` of the container that supplies
the bound. So the bound comes down to the id type instead:
`dereplicating()` now asserts `nextseqtab.size() == data.sequence_count()`
and iterates to that `unsigned int` count, matching the
`const auto amplicons = data.sequence_count();` idiom already at
`algo.cpp:298` and `utils/algod1_network.cpp:169`.

### Verification

DEBUG build warning-free on x86-64; `aarch64`, `ppc64le` and mingw
cross-builds clean; `cppcheck` clean on both files; suite runs to
completion, 1066 PASS / 0 FAIL.

**What should be recorded for the rest of the item:** `unsigned int` is the
intended amplicon- and cluster-id type, so the remaining twenty-odd `0U`
loops are correct as they stand and should not be swept to `std::size_t`.
`std::size_t` belongs where a value really is a size or an offset into a
container — which is where the tree already uses it (`Span`, `View`,
`line_buffer`, `algo_internal.hpp:119`) — and not where the value is an
amplicon id that happens to be used as a subscript.

## T5 — stop passing std containers as raw pointers

*"Avoid passing std data structures as raw pointers. Search and replace
calls to `.data()`"* [2026-08-08]

**Not started.** Inventory below is measured; everything else is a plan.

47 `.data()` call sites across `.cpp` and `.hpp`. They do not all mean the
same thing, and a blanket search-and-replace would break several, so the
first job is the split:

| group | sites | disposition |
|---|---|---|
| A — inside the view/span accessors themselves | 12 | keep: this *is* the abstraction |
| B — C and OS API boundaries | 8 | keep: the pointer is the contract |
| C — swarm's own functions taking raw pointers | ~14 | the actual target |
| D — pointer arithmetic on a container's storage | ~5 | target, but needs `Span`/`View`, not a signature swap |
| E — deliberate, already documented | 8 | keep, and do not "fix" |

Group A is `utils/view.hpp` (6), `utils/decimal_digits.hpp` (3),
`utils/span.hpp`, `utils/view_stream.hpp`, `utils/print_view.hpp`. These
implement `data()` or consume it one level below the abstraction.

Group B is `sysctl(mib.data(), …)` (`os/macos/system_memory.cpp:45`),
`getopt_long(…, long_options.data(), …)` (`cli.cpp:457`),
`destination.append(digits.data(), digits.size())` (`utils/cigar.cpp:58`,
`std::string::append` takes a pointer and a length), and the four
`std::memcpy` calls in `set_lane_8` / `set_lane_16`
(`search8.cpp:711,713`, `search16.cpp:460,462`) — those exist precisely
*because* they are byte-wise, see `4ce3682`.

**Group C is the item.** The clearest cases are the score-profile
builders:

```
dispatch_dprofile8(cpu_features, dprofile.data(), score_matrix, dseq.data())
```

at `search8.cpp:843,908` and `search16.cpp:593,660`. The declaration
(`arch/*/search_dispatch.hpp`) is `unsigned char * dprofile,
unsigned char const * score_matrix, unsigned char const * dseq` — three
same-family pointers in a row, which is also an easily-swappable-parameter
hazard of the kind CLAUDE.md calls out. `dprofile_v` is a
`std::vector<BYTE>` (`utils/search_data.hpp:54`) and `dseq` a
`std::array`, so both have a size the callee currently cannot see.

Group D is the `dirbuffer.data()` bounds arithmetic
(`search8.cpp:926`, `search16.cpp:678`) and `q_start.data()` reinterpreted
as `VECTORTYPE **` (`search8.cpp:828`, `search16.cpp:577`). These are not
signature changes — the pointer is being *walked*, so they want a `Span`
or a `View` rather than a reference.

**Group E is the trap, and the reason this task needs care rather than
sed.** T2 group B established that `.data()` *destroys* information: it
returns `unsigned char const *` and throws away the `alignas(16)` on
`Qgram_vector`, which is why the three SIMD qgram kernels cast from
`&lhs` and **not** from `lhs.data()`, each with a comment saying so
(`arch/{x86_64,aarch64,ppc}/qgram_compare.cpp`, `arch/x86_64/popcnt.cpp`).
Conversely `arch/portable/qgram_compare.cpp` keeps `.data()` on purpose,
because it `memcpy`s bytes instead of loading vectors. So in this codebase
some `.data()` calls are the bug and one is the fix. See also the
mechanism note under T2: `reinterpret_cast<__m128i *>(blk.data())` warns
where `reinterpret_cast<__m128i *>(block_ptr)` does not.

Notes for whoever picks this up:

- the tree already has the vocabulary — `Span<T>`, `View<T>`,
  `Sequence`, `He_block`, `Qgram_vector` — so this is mostly about
  reaching for it, not building it
- prefer `Span`/`View` over `T *` + separate length, and a
  reference-to-array (`Type const (&)[Size]`, as in `utils/fatal.hpp:64`
  and `utils/print_view.hpp:105`) where the extent is fixed
- the three `dispatch_dprofile*` declarations exist once per architecture,
  so any signature change lands in three headers plus `sse41`/`ssse3`
- `search8.cpp` / `search16.cpp` are the hot kernels. T2 group A's lesson
  applies directly: inlining `.data()` at a cast site and dropping the
  local cost two prologue instructions and 16 bytes of `search8`. Diff the
  disassembly, and normalise **both** forms of objdump's jump targets
- expect no measurable win; this is a typing and API-surface change. Bound
  the mechanism before benchmarking, per T1 and T2 group B
